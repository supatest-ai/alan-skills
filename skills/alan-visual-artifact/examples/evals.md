# Skill Evals

## Should invoke internally

1. Create a rich visual plan for this cross-service migration and pick the right diagram.
2. Render an interactive HTML artifact explaining this architecture decision.
3. Visualize this stateful recovery path in the test report.
4. Turn the implementation plan into an evidence-backed diagram and document.
5. Show how the requirements, tasks, tests, and PR evidence connect.
6. Let me inspect the plan, test, and review paths through this dense architecture.
7. Prototype the failure and retry behavior before we implement the real approval flow.

## Fidelity expectations

1. A short linear implementation plan stays in Markdown.
2. A plan with two competing architectures uses a comparison plus one topology diagram.
3. A dense architecture with four named request paths uses the interactive-diagram profile.
4. An unresolved navigation hierarchy uses a wireframe, not a prototype.
5. An accepted structure awaiting visual finish uses a mockup, not a wireframe.
6. A stateful recovery risk uses a bounded prototype with a visible simulated boundary.

## Should not invoke

1. Fix the API validation bug and add a unit test.
2. Explain what a sequence diagram is.
3. Publish this artifact to an external hosting service.
4. Rebuild the Alan settings screen as a production interface.
5. Add animation to make this ordinary status report more engaging.

The primitive is normally called by an existing Alan workflow, not advertised as a separate user workflow.
